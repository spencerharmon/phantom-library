# M14 ledger evaluation — channel refactor state

Date: 2026-06-23

This document records the required evaluation for PLAN.md M14 `EVALUATE` rows against the current channel architecture. It does not convert scope to `DEFER` or `DROP`; operator approval remains required for any requirement not implemented.

| Requirement | Current channel-refactor finding | Still relevant? | Implementation / disposition |
|---|---|---|---|
| REQ-M14-RECOMMENDATIONS | Current discovery pipeline ingests TMDB catalogue rows and availability probes; no channel-era code ingests favourite-similar/recommendation rows from a user's favourites. `DiscoveryRefreshTask` has a TODO for favourite-based refresh input, and `UserDataSavedListener` now handles favourite-triggered materialisation only. | Yes, if operator still wants recommendation expansion beyond catalogue discovery. | Not implemented in this change. Requires operator disposition or a dedicated recommendation-ingestion implementation with tests for user favourite input → TMDB similar/recommendations → catalogue/availability rows. |
| REQ-M14-RETENTION | Schema v11 intentionally separates append-only `catalogue_items` from availability state. Admin UI labels `PhantomRetentionDays` as disabled/no-op, so config no longer implies active pruning. `EvictionSweeper` still handles materialised-file eviction, not catalogue pruning. | Catalogue retention is not needed for correctness under append-only design; materialised-file eviction remains relevant and implemented. | Implemented as config/UI cleanup: retention field disabled/no-op in `configPage.html`; no destructive catalogue pruning added. Tests: `ConfigPageMarkupTests` plus full unit suite. |
| REQ-M14-VAULT | `IGostreamClient` exposes Vault Mode `PrestageAsync`, `UnprestageAsync`, and a presence probe. These are now driven end-to-end by `VaultManager` (`Materialisation/VaultManager.cs`): the favourite path prestages the materialised stub, de-favourite/eviction unprestage it. Materialised rows also remain protected from eviction by existing favourite protection in `EvictionSweeper`. | Yes — implemented. | Implemented. `VaultManager` bridges the favourite/eviction lifecycle to gostream Vault Mode. A favourite save on a channel movie/episode (save reason `UpdateUserRating` or `UpdateUserData`) materialises then prestages the stub at `VaultPrestagePriority`; a de-favourite unprestages it; `EvictionSweeper` unprestages before removing a stub. Prestage is gated on new `VaultModeEnabled` (default on); unprestage is deliberately ungated so turning Vault Mode off drains footprint rather than stranding it. Best-effort (presence-probed, failures swallowed). Movie/episode parity throughout. Tests: `VaultManagerTests`, `UserDataSavedListenerTests`, `EvictionSweeperTests` (full suite green). Live rig verification against a gostream with Vault Mode endpoints remains an operator step (unit tests cannot exercise the real prestage HTTP path). |
| REQ-M14-CONCURRENCY | `MaterialisationQueue.GetIndexerLimit()` enforces `MaterialisationConcurrencyPerIndexer` via per-indexer `SemaphoreSlim`; `MagnetSelector` probes enabled indexers sequentially, so source probing never exceeds one request per indexer in current code. Config no longer overpromises parallel probing behavior because materialisation queue cap exists and probing is naturally below cap. | Yes, for materialisation workers; source probing cap is effectively <= 1. | Implemented by existing queue cap and sequential probe behavior; full unit suite remains green. |
| REQ-M14-SEARCH-GATING | Native Jellyfin remote-search providers (`TmdbMovieRemoteSearchProvider`, `TmdbSeriesRemoteSearchProvider`) return TMDB metadata search results only. Channel visibility/playability is gated by `availability_items`, materialised state, and channel browse paths, not native remote search. | No separate native remote-search availability gate needed unless operator wants remote-search results hidden by source availability. | No code change required for current channel contract; availability gating stays channel-only. Operator disposition needed only if remote-search hiding is desired. |
| REQ-M14-SPLASH | Channel playback now uses native `RequiresOpening` media sources. Rig scenarios assert unmaterialised movie/episode PlaybackInfo has no splash/file path and auto-open returns real gostream file. Splash asset/code remains as legacy support but is not the active playback handoff. | Historical/support only. | Verified by `35-channel-e2e-playback.sh` and `36-channel-episode-e2e-playback.sh`; no cleanup required for active UX. |
